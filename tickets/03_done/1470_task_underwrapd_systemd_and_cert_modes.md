## Problem

The frontend daemon (`underwrap-<inst>` service, generated by
`nix/modules/underwrap.nix`) is the only target-host process that
holds:

- the runtime mTLS client cert and key on disk
  (`${stateDir}/client-${instName}.pem`, `.key`)
- every live wrapper-resource channel (the daemon side of each
  socketpair)
- cached resource blobs for the lifetime of each open invocation
- audit log output to journald

A compromise of this process on the target host is effectively a
compromise of the runtime client identity. The attacker can call
`/v1/wrappers`, `/v1/wrapper-invocations`, and
`/v1/wrapper-invocations/finalize` against the backend as a
legitimate client. The backend's policy gate (`Locked` / `Unlocked`
per `(client_instance, wrapper, resource)`) still applies, but
that's a policy constraint, not isolation.

Two concrete things to tighten:

### Systemd unit hardening

Today the generated unit (search `nix/modules/underwrap.nix` for
`service = { ... }`) probably sets minimal isolation. The daemon
needs very little: filesystem read of `${stateDir}`, write of audit
to journald, outbound TCP to the backend, listen on a few Unix
sockets under `${runDir}`. Everything else can be locked down.

### Client cert/key file modes

`docs/security.md` claims:

> The mTLS client cert and key, and the backend admin token, retain
> their default ownership and mode (readable only by the daemon user
> that needs them).

The NixOS module sets `${stateDir}` to mode `0700` owned by the
daemon user (the existing `tmpfiles` entry). The files themselves
are produced by `underwrap-keygen` running as the operator; their
modes after generation depend on what `underwrap-keygen` writes
them with, not what the module declares.

Worth verifying end-to-end that the produced files are mode `0600`
owned by the daemon user, *and* asserting this at daemon startup so
a misconfiguration is caught loudly rather than relied on.

## What to do

### Systemd unit (`nix/modules/underwrap.nix`)

In `mkInstance`'s `service.serviceConfig`, add (or verify already
present):

- `NoNewPrivileges = true;`
- `ProtectSystem = "strict";`
- `ProtectHome = true;`
- `PrivateTmp = true;`
- `PrivateDevices = true;`
- `ProtectKernelTunables = true;`
- `ProtectKernelModules = true;`
- `ProtectKernelLogs = true;`
- `ProtectControlGroups = true;`
- `ProtectClock = true;`
- `ProtectHostname = true;`
- `ProtectProc = "invisible";`
- `ProcSubset = "pid";`
- `RestrictAddressFamilies = [ "AF_UNIX" "AF_INET" "AF_INET6" ];`
- `RestrictNamespaces = true;`
- `RestrictRealtime = true;`
- `RestrictSUIDSGID = true;`
- `LockPersonality = true;`
- `MemoryDenyWriteExecute = true;`
- `SystemCallArchitectures = "native";`
- `SystemCallFilter = [ "@system-service" "~@privileged @resources" ];`
- `ReadWritePaths = [ runDir stateDir ];`
- `ReadOnlyPaths = [ "/etc/underwrap" ];` (if not already covered by
  `ProtectSystem=strict`)
- `UMask = "0077";`
- `CapabilityBoundingSet = "";` (the daemon needs no caps)
- `AmbientCapabilities = "";`
- `IPAddressAllow = ...;` if the backend address is statically
  knowable from the instance config — otherwise leave open

Walk the resulting unit through `systemd-analyze security
underwrap-<inst>` and aim for a score better than 2.0 ("OK") and
ideally under 1.0 ("safe"). The aggressive flags above should land
near the lower end.

### Client cert/key modes

1. Inspect what `underwrap-keygen` writes for the cert/key files
   (`crates/...` — find the keygen entry point). Ensure both are
   produced mode `0600`. If they aren't, fix the writer.

2. In `crates/frontend-underwrapd/src/startup.rs` (or wherever the
   daemon opens the cert/key on boot), `stat` the files before
   loading and refuse to start if:
   - the owner is not the daemon's effective UID, or
   - the mode is wider than `0600`, or
   - the parent directory is wider than `0700`.

   Aborting at startup is consistent with "no silent fallback". The
   error message should name the offending file and the expected
   mode/owner.

3. Add a VM-test assertion that the cert and key files are mode
   `0600` owned by the daemon user after a fresh deploy.

### Doc

Update `docs/security.md` §"What the central backend is trying to
buy you" (or add a new §"Target-host daemon" section) explicitly
listing the systemd hardening and the startup mode-check. The
current doc claim "readable only by the daemon user that needs
them" should be backed by the startup-time assertion, not just
operator discipline.

## Resolution (2026-05-27) — code complete, VM-acceptance gated on 1570

**Systemd unit** (`nix/modules/underwrap.nix`, `mkInstance`
`serviceConfig`): added the remaining hardening directives on top of
what 1550 already carried — `ProtectKernelLogs`, `ProtectProc =
"invisible"`, `ProcSubset = "pid"`, `RestrictNamespaces`,
`CapabilityBoundingSet = ""`, `AmbientCapabilities = ""`,
`SystemCallFilter = [ "@system-service" "~@privileged @resources"
"@chown" ]`, and explicit `ReadOnlyPaths = [ stateDir "/etc/underwrap"
]`. `@chown` is re-added after the `~@privileged` removal because the
daemon chowns its wrapper socket to the instance group in
`startup::bind_socket` — without it socket setup would SIGSYS.
`ReadWritePaths` stays `[ runDir ]` (the daemon only *reads* the cert/key
under `stateDir` at runtime; keygen writes them out-of-band).

**Cert/key modes:**
- `frontend-keygen` now writes the client **cert** at `0600` (was
  `0440`); the key was already `0400`.
- New `startup::check_credential_permissions` (called from
  `server::run` right after `validate_config`) refuses to start when a
  *present* credential file is owned by another uid, is wider than
  `0600`, or sits in a parent dir wider than `0700`. Absent files are
  tolerated (self-heal before keygen runs). Unit tests cover
  accept-0600, reject-group-readable, reject-world-dir, tolerate-missing.
- The integration-test PKI harness (`harness/pki.rs`) now writes its
  client cert/key `0600` and the `pki` dir `0700` to satisfy the check.

`cargo test --workspace`, clippy, and fmt are green. The module parses.

**Correction during 1570 (2026-05-27):** two of the directives the
ticket listed are unsafe *for this daemon* and were dropped/adjusted:

- `ProtectProc = "invisible"` was **removed**. The daemon's wrapper
  peer-auth reads the *connecting* process's `/proc/<pid>/status` to
  resolve its effective GID, and that peer runs as a different
  unprivileged user. `invisible` hides other users' `/proc` entries,
  which would break the kernel-rooted identity check. `ProcSubset =
  "pid"` is kept (it only hides non-process `/proc` files).
- `SystemCallFilter` no longer removes `@resources`. The daemon calls
  `setrlimit(RLIMIT_CORE, 0)` at startup (`main.rs`), which lives in
  `@resources`; stripping it would SIGSYS the daemon on boot. The filter
  is now `[ "@system-service" "~@privileged" "@chown" ]`.
