## Scope and non-goals

### Scope

- Eventually assess and resolve every accepted final finding F-001–F-058 through
  approved, coherent, sequential tickets.
- Preserve finding priority, security-boundary meaning, dependencies, and the
  report's distinction between corrections and intentional behavior choices.
- Before each approved ticket's fix, deliberately seek valuable behavior-
  preserving simplifications across the repository and commit accepted cleanup
  as independently reviewed units.
- Maintain enough durable state here for every later ticket and decision to use
  outcomes from previous cleanup and fix work.

### Non-goals

- This bootstrap does not derive ticket filenames, hierarchy, grouping, or
  implementation tasks. It identifies F-001 only as the next candidate.
- There is no one-time broad refactor before review remediation. Optional
  formatting or renaming without concrete simplification value is not cleanup.
- Opportunities O-001–O-026 are not findings and are not approved behavior
  changes. They require separate explicit behavior approval.
- Unresolved items U-001–U-011 are not findings or tickets. They require the
  evidence or decision identified by the report and separate approval before
  work is created from them.
- Report acceptance does not approve dependencies, changes to the
  `underwrap-exec → underwrap-ns` binary chain, weakened security boundaries, or
  any other decision that `AGENTS.md` requires the user to approve.
- Do not include secret values, credentials, resource blobs, tokens, or key
  material in this file, tickets, commits, logs, or prompts.

## Immutable operating protocol

1. The parent/controller is the sole agent/controller decision-maker, subject to
   the user approvals and conditions in this protocol. It owns delegation,
   synthesis, scope control, and final repository state; assigned writer and
   fix-worker subagents edit only within their approved role/scope.
2. Begin directly in critical. Process severity in order critical → high →
   medium → low. There is no critical-entry gate. Immediately before each
   transition critical → high, high → medium, and medium → low, use `ask_user`
   with comment entry enabled and record the response. Do not transition without
   approval.
3. A lower-severity finding may move earlier only when it is a necessary
   prerequisite for current approved work. Record the dependency, necessity,
   controller decision, and resulting order in the decision log and ledger.
4. Materialize exactly one ticket file at a time—normally one task-only ticket,
   with no simultaneous parent/child hierarchy—under the existing ticket
   workflow. During materialization, this named program may write only that one
   todo ticket and this handover; the report, source, tests, configuration, and
   published docs remain read-only. Then stop and use `ask_user` with comment
   entry enabled for explicit approval before implementation or an in-progress
   move.
5. Ticket approval is explicit and ticket-specific. Report acceptance, a band-
   transition approval, generic continuation, or ticket creation is not
   implementation approval. Record approval comments and conditions faithfully.
   Rejection or requested changes leave the ticket out of in-progress and permit
   only revision/re-presentation of that same file, or stopping—not creation of
   another ticket.
6. After approval, run a cleanup-discovery phase before the actual finding fix.
   Direct the implementation worker to seek ticket-local and repository-wide
   behavior-preserving simplifications with concrete net reduction in
   complexity, duplication, or dead structure. Keep this phase attached to the
   current fix-led ticket; do not launch a broad preliminary refactor.
7. Reject optional formatting/renaming and cleanup without concrete reduction.
   Every cleanup must be coherent, independently reversible, and always
   behavior-preserving. User approval does not convert behavior-changing or
   boundary-weakening work into cleanup; handle it only as separately approved
   fix or Opportunity scope. Cleanup must not add dependencies, change the
   `underwrap-exec → underwrap-ns` chain, expose secrets, or settle/absorb an
   unresolved decision without `ask_user`. Opportunities and U-items retain
   separate approval.
8. For each accepted simplification, isolate one coherent cleanup unit. Give it
   a fresh independent review, a separate fix-worker pass if the controller
   accepts review corrections, focused and boundary-required validation, and a
   controller acceptance/sanity/scope/diff/security check. Then commit it alone
   as type `cleanup`, with the corresponding handover update, before any finding
   fix commit. If corrections require another coherent commit, classify it as
   cleanup and repeat the full cycle.
9. The first committed unit after ticket approval—first cleanup commit when any
   is accepted, otherwise the first fix commit—must move the ticket from todo to
   in-progress and make that state and approval durable. An approval-pending todo
   ticket may remain untracked: preserve its content at the in-progress path and
   include the old todo path in the staged allowlist only if it was tracked.
   Otherwise stage the new in-progress path, this handover, and the coherent
   implementation paths.
10. After cleanup is exhausted or explicitly records that no valuable cleanup
    was accepted, implement the finding correction in one or more coherent fix
    units. Each receives fresh independent review, a separate fix-worker pass
    for controller-accepted corrections, focused and boundary-required
    validation, and the controller's independent checks before its `fix` commit.
11. A ticket may have multiple cleanup and fix commits. Record every
    implementation commit in order with type, scope, review, fixes, validation,
    controller check, affected findings, and hash/subject. The final fix commit
    moves the ticket to done and records final outcome/validation. Do not include
    unrelated paths in any commit.
12. After that final fix commit, present the completed outcome, ordered commits,
    validation, reviewer result, controller sanity check, handover decisions,
    and effects on later findings; then use `ask_user` with comments enabled. If
    changes are requested, record `completion changes requested`, move the same
    ticket back to in-progress, and run another coherent fix/review/validation/
    commit cycle. Do not prepare another ticket. If accepted, record acceptance
    and continuation authorization. Persist completion-review and transition
    responses in exact-allowlist handover-only `control` commits outside the
    ticket's ordered cleanup/fix sequence; these commits also replace preceding
    `SELF` placeholders with immutable hashes. A following severity-transition
    gate occurs only after completion acceptance.
13. If cleanup changes, invalidates, or resolves evidence for another F-id,
    immediately update that finding's ledger entry and record the cleanup commit
    and effect. On reaching that F-id, revalidate current evidence and link the
    completed work instead of creating a duplicate ticket. Do not treat this as
    approval for any Opportunity or U-item.
14. Use one implementation writer subagent, separate fresh reviewer subagent(s),
    and a separate fix-worker subagent for controller-accepted corrections.
    Repeat review/fix as needed. Stop for `ask_user` if an unapproved product,
    architecture, dependency, binary-chain, behavior, unresolved-item, or
    security-boundary decision is required, or a blocker prevents safe work.
15. The controller independently checks acceptance criteria, scope, sanity, the
    actual diff, security invariants, validation, and absence of unrelated work
    for every cleanup and fix unit. Subagent review does not replace this check.
16. Update this handover after ticket creation and approval, every cleanup/fix
    unit and review/fix round, every implementation commit, completion review,
    transition gate, and control commit. Later decisions must use the recorded
    outcomes and accumulated lessons.
17. The initial workflow-setup commit contains only `AGENTS.md`,
    `tickets/_review/codebase_2026-07-18.md`, and this handover file. No ticket,
    cleanup, or finding-fix work belongs in that commit.
18. Follow `.pi/skills/underwrap-ticket-workflow/SKILL.md` for ticket content,
    validation, moves, and exact staging. For this named program, all-58 scope
    supersedes normal low deferral; materialization's read-only rule is overridden
    only for the single new todo ticket plus this handover; and the cleanup-first
    multi-commit/control-commit protocol supersedes the one-commit task loop.
    All other safety and preflight rules remain binding.

## Session-resume checklist

1. Read `AGENTS.md`, this file, the complete source report, and
   `.pi/skills/underwrap-ticket-workflow/SKILL.md`.
2. Run `git status --short` and `git diff --cached --name-only`. Preserve
   pre-existing changes. Stop if unexplained staged or overlapping changes make
   exact-scope action unsafe; never unstage another user's work.
3. Compare current HEAD/relevant files with the baseline. Revalidate any selected
   or cleanup-affected finding touched by intervening commits.
4. Read current band, transition table, decision log, registry and ordered
   commit sequences, finding ledger, constraints, and lessons. Identify the last
   completed unit and apply its outcomes to the next decision.
5. Confirm there is at most one materialized incomplete program ticket. Search
   todo, in-progress, and done for overlap before creating anything.
6. If a ticket exists, verify its exact approval/comments, durable board state,
   cleanup state, completion-review state, and first incomplete registry step.
   A rejected or revision-requested todo ticket may only be revised and
   re-presented. A `completion changes requested` ticket returns from done to
   in-progress for the same ticket's next fix cycle. Never infer approval from
   status, chat, transition approval, or a done/committed board state.
7. If the latest ticket is committed but completion review is pending, present
   its outcome, ordered cleanup/fix commits, validation, reviewer result,
   controller check, handover decisions, and later-finding effects; then use
   `ask_user` with comments enabled. Persist the response in a handover-only
   control commit and resolve preceding `SELF` placeholders. Until explicit
   acceptance and continuation authorization are recorded, do not prepare or
   derive another ticket. If continuation crosses a band, perform and persist
   the distinct transition gate afterward.
8. If an approved ticket is still in todo, the next committed cleanup or fix
   unit must include its move to in-progress. If cleanup is incomplete, finish
   cleanup discovery and each accepted cleanup's independent cycle before any
   actual finding fix.
9. If no ticket exists, ensure the current band is active (or its transition is
   approved), choose the smallest coherent next work after fresh evidence and
   overlap checks, create one task-only ticket and update only that ticket plus
   this handover, then stop for ticket-specific `ask_user` approval with comments.
10. Before each implementation commit, inspect the exact diff, run focused and
    boundary checks, verify staged allowlist/secret hygiene, and label it cleanup
    or fix. For the final fix commit, move the ticket to done and record final
    outcome/validation. Handover-only control commits contain only this file and
    record post-commit user/transition decisions.

## Accumulated lessons

- Test helpers should return only the capability current tests consume; retaining
  decoded response metadata behind dead-code suppressions obscures test intent.
- Removing an unused test-only scope helper narrows F-043 evidence but does not
  address its production no-op wire/environment field or duplicate config. Later
  F-043 work must revalidate production evidence and link cleanup sequence 2.
- Cleanup discovery rejected abstractions that would consolidate the current
  lossy F-001 path; simplification must not make an imminent defect easier to
  preserve.
- A lossy flat projection is suitable only as a read/list view. Slot-scoped
  mutation must select and update the canonical typed aggregate so unrelated
  sections survive the load-modify-save cycle.
- Test fixtures should model one instance socket and one unified listener as
  singleton capabilities rather than duplicate them per wrapper or request role.
- Rare parallel integration authentication failures may be consistent with the
  pre-existing release-before-bind port race, but this is not proven and does not
  authorize O-024 fixture redesign; preserve the evidence for later review.
- A bulk outer frame bound does not constrain an inner vector soon enough: read
  and validate the inner resource length before allocating/copying its body, and
  retain message-level checks even when outer arithmetic would admit the payload.
- Validate the fully composed target environment, including NUL-free values and
  valid keys from resource, fixed, and passthrough sources, during pure host
  planning before namespace, mount, staging, helper, UID, or target effects.
- Exact-one journal evidence must observe arrival, allow a bounded post-completion
  ingestion interval, then re-query the entire cursor-scoped set; stopping at the
  first record proves existence, not uniqueness.
- Structured audit sinks must encode operator-facing metadata for the sink:
  journald values containing newlines require native binary framing, while stderr
  fallback requires valid one-line JSON escaping. Trusted operator input is not a
  reason to corrupt audit structure.
- Complete-resource limits must be budgeted independently from publication-body,
  generic-control, HTTP/base64, message-envelope, and outer-prefix bounds. ACK
  size eligibility remains distinct from caller receipt and backend durability.
- A NixOS hardening assertion must inspect the final typed configuration consumed
  by a generator, not only a convenience option that contributes to it. When a
  freeform consumer grammar is security-relevant, use a simple fail-closed
  superset that cannot miss accepted spellings, while retaining the consumer's
  swap-versus-filesystem distinction to avoid unrelated boundary expansion.
- A default public trait convenience method with no call, override, macro use, or
  workspace consumer still widens the API and error surface. Under the greenfield
  posture, exhaustive reachability plus full workspace validation can justify
  deleting that dead structure as an independently reversible cleanup.
