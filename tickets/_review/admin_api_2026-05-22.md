### F-001 — `stores.rs` is 1 289 lines and mixes CRUD with lifecycle

- **Category:** Module boundaries & file size
- **Severity:** must-fix
- **Scope:** in-component
- **Location:** `crates/backend-backendd/src/admin_api/stores.rs` (whole
  file).
- **Observation:** `stores.rs` bundles two distinct concerns:
  - **CRUD** (`handle_admin_stores_list`, `handle_admin_store_detail`,
    `handle_admin_store_create`, `handle_admin_store_update`,
    `handle_admin_store_delete`, plus the `admin_store_*` projector
    helpers and `admin_store`/`resolve_store_dir`) — lines 1–710 ish.
  - **Lifecycle** (`handle_admin_store_rotate_key` + `reencrypt_into` +
    `rotation_lock` + `handle_admin_store_unlock` + `do_admin_store_unlock`
    + `handle_admin_store_lock`) — lines 712–1196.

  The two concerns touch completely different surfaces: CRUD edits the
  registry record + name uniqueness; lifecycle re-encrypts on disk,
  parses hex keys, manages the rotation `Mutex`, and verifies the unlock
  canary. They share only `admin_store_audit` (one helper), the
  `admin_store()` resolver, and `create_data_dir_secure`. The
  `CLAUDE.md` ceiling is ~600 lines; this is 1 289.
- **Recommendation:** Split into a submodule:

      stores.rs → stores/mod.rs (route, admin_store, audit helper, projectors)
                  stores/crud.rs (list, detail, create, update, delete)
                  stores/lifecycle.rs (unlock, lock, rotate-key, reencrypt_into, rotation_lock)

  `admin_store_actions`, `admin_store_usage`, `admin_store_usage_for_locked`,
  `admin_store_list_item`, `admin_store_detail`, `backend_kind`,
  `saturating_u32`, `resolve_store_dir` stay in `mod.rs` (used by both
  CRUD and lifecycle response building). `generate_master_key_bytes`
  and `master_key_hex` move to `lifecycle.rs` (only used during create
  + rotate; `create` is in CRUD but the helpers can live with rotate-key
  and be `pub(super)` imports).

  The `route()` dispatcher stays in `mod.rs`, since it's the public
  surface and is also where the path-strip-suffix matchers live for
  `/rotate-key`, `/unlock`, `/lock`.

- **Behavior change?** no.
- **Related tickets:** none — the previous epic's modularization
  stopped at the crate root, not at oversized submodules.

### F-003 — Three different patterns for "split body-parsing from handler"

- **Category:** Naming & terminology
- **Severity:** must-fix
- **Scope:** in-component
- **Location:**
  - **`*_endpoint` wrapper + body-taking handler** —
    `policy.rs:127-172` (`handle_admin_wrapper_permissions_list_endpoint`,
    `handle_admin_wrapper_permission_upsert_endpoint`,
    `handle_admin_wrapper_permission_delete_endpoint` each wrap their
    body-taking sibling); `pairs.rs:20-59`; `resources.rs:29-115`;
    `secrets.rs:59-76, 130-146` (only for `write` and `rename`).
  - **`handle_admin_X` + `do_admin_X` pair** — `users.rs:119-128 /
    132-191`, `:194-205 / 208-249`; `client_instances.rs:166-176 /
    178-292`, `:294-305 / 307-437`; `stores.rs:293-303 / 310-462`,
    `:500-511 / 514-597`, `:1047-1062 / 1065-1159`.
  - **No split at all** — `auth.rs::handle_admin_login`,
    `auth.rs::handle_admin_password_change`, `bootstrap.rs::handle_admin_bootstrap`,
    `secrets.rs::handle_admin_secret_read`,
    `secrets.rs::handle_admin_secret_list`,
    `secrets.rs::handle_admin_secret_delete` do the JSON parse
    in-place.
- **Observation:** All three patterns exist for the same reason — the
  body-taking sibling is unit-testable; the wrapper just runs
  `parse_json_body` and dispatches. The reader has to learn three
  conventions in one file. Within `secrets.rs` there are even two
  patterns (read/list/delete vs write/rename) for the same kind of
  endpoint. The choice between "split for tests" and "don't bother"
  also looks arbitrary — `handle_admin_secret_read` could just as well
  be unit-testable but isn't split.
- **Recommendation:** **Decision needed.** Pick one of:
  1. The `*_endpoint` + body-taking pair, applied wherever a unit
     test wants to drive the handler without a `Request<Incoming>`.
     Rename every `do_admin_X` to `handle_admin_X` and the parser to
     `handle_admin_X_endpoint`. Keep endpoints whose handler isn't
     unit-tested as a single function.
  2. The `do_admin_X` pair, applied the same way.
  3. Drop the split entirely and write tests against
     `handle_admin_request` end-to-end (relies more on Playwright
     for coverage).

  My recommendation is option 1 — `*_endpoint` reads better at the
  `route()` dispatch table (each row visibly takes a `request` and
  parses), and the body-taking sibling drops the `_endpoint` suffix
  and is what unit tests reach for. This is a naming change only; no
  behaviour moves. Flag as **must-fix** because cross-file
  inconsistency is the single biggest readability papercut in the
  subtree, but the recommendation itself is a judgement call.

- **Behavior change?** no.

### F-004 — Double `admin_store()` lookup in two secret handlers

- **Category:** Simplification (same behaviour)
- **Severity:** must-fix
- **Scope:** in-component
- **Location:**
  - `crates/backend-backendd/src/admin_api/secrets.rs:59-76`
    (`handle_admin_secret_write_endpoint`) calls `admin_store(state,
    &body.store)` purely to check existence, then delegates to
    `handle_admin_secret_write`, which calls `admin_store(state,
    &body.store)` *again* at line 168 to get the actual handle.
  - Identical shape in `secrets.rs:130-146`
    (`handle_admin_secret_rename_endpoint`) → `handle_admin_secret_rename`
    at line 214.
- **Observation:**

      pub(crate) async fn handle_admin_secret_write_endpoint(...) -> ... {
          let body = parse_json_body::<...>(request).await?...;
          match admin_store(state, &body.store) {
              Ok(_) => handle_admin_secret_write(state, actor, body),   // <-- ignored Ok
              Err(resp) => resp,
          }
      }

      pub(crate) fn handle_admin_secret_write(...) -> ... {
          ...
          let store = match admin_store(state, &body.store) {           // <-- second lookup
              Ok(store) => store,
              Err(resp) => return resp,
          };
          ...
      }

  Each call grabs the stores `RwLock` read guard, does a `HashMap`
  lookup, and (for unlocked stores) clones an `Arc`. Two of those for
  one request is harmless functionally but reads as a bug. The two
  helpers should fold into one.

- **Recommendation:** Delete the existence check from
  `handle_admin_secret_write_endpoint` and
  `handle_admin_secret_rename_endpoint`. Move the JSON-parse-only
  responsibility into the `*_endpoint` and let the body-taking handler
  do the single `admin_store()` lookup it already does.

  If the F-003 cutover happens in the same epic, this fix collapses
  naturally as part of unifying the pattern — only the
  `parse_json_body` call survives in `*_endpoint`.

- **Behavior change?** no (an unknown-store response still ends up the
  same; the second lookup is just gone).

### F-005 — `policy.rs::handle_admin_policy_put` hand-rolls a write instead of using `save_policy_document`

- **Category:** Duplication / missed reuse
- **Severity:** must-fix
- **Scope:** in-component
- **Location:** `crates/backend-backendd/src/admin_api/policy.rs:100-125`.
- **Observation:**

      pub(crate) async fn handle_admin_policy_put(...) -> Response<...> {
          let body = parse_json_body::<...>(request).await?...;
          match admin_store(state, &body.store) {
              Ok(store) => {
                  let write_result = serde_json::to_vec(&body.document)
                      .map_err(anyhow::Error::from)
                      .and_then(|bytes| store.write(POLICY_DOCUMENT_SECRET_ID, bytes.as_slice()));
                  ...
              }
              Err(resp) => resp,
          }
      }

  Every other policy mutator in the file — `drop_client_instance_permissions`,
  `handle_admin_wrapper_permission_upsert`,
  `handle_admin_wrapper_permission_delete` — goes through
  `save_policy_document(store.as_ref(), &doc)` from
  `crate::storage::documents`. Only `handle_admin_policy_put` reaches
  past the helper to call `serde_json::to_vec(...)` +
  `store.write(POLICY_DOCUMENT_SECRET_ID, ...)` itself.

  Previous review's ticket 1020 collapsed `load_policy_document*` into
  one helper but didn't sweep the write side. The risk is divergence —
  if `save_policy_document` ever adds canonicalisation, validation, or
  audit hooks, this code path silently skips them.
- **Recommendation:** Replace the inline serialize+write with
  `save_policy_document(store.as_ref(), &body.document)`. Drop the
  `POLICY_DOCUMENT_SECRET_ID` import from this module if no other
  caller remains.
- **Behavior change?** no — `save_policy_document` is implemented as
  the same serialize+write today (verified by reading
  `storage/documents.rs`); the change is just consistency.

### F-006 — Two near-identical "generate id then retry on collision" loops

- **Category:** Duplication / missed reuse
- **Severity:** nice-to-have
- **Scope:** in-component
- **Location:**
  - `stores.rs:325-336` (`do_admin_store_create`):

        let store_id = loop {
            let candidate = generate_store_id();
            if !state.stores.read().unwrap().records.contains_key(&candidate) {
                break candidate;
            }
        };

  - `client_instances.rs:210-220` (`do_admin_client_instance_create`):

        let id = loop {
            let candidate = generate_client_instance_id();
            if !state.client_instances.read().unwrap().contains_key(&candidate) {
                break candidate;
            }
        };

- **Observation:** Same loop, same purpose, two `RwLock<HashMap>`
  shapes. Both ids come from `crate::ids::random_id`, which already
  provides ~80 bits of entropy — the loop is essentially a paranoia
  guard. The duplication is mechanical.
- **Recommendation:** Add a small helper next to `crate::ids::random_id`:

      pub(crate) fn fresh_id<F: Fn(&str) -> bool>(prefix: &str, exists: F) -> String {
          loop {
              let candidate = random_id(prefix);
              if !exists(&candidate) {
                  return candidate;
              }
          }
      }

  Each call site shrinks to one line:

      let store_id = crate::ids::fresh_id("store", |c| {
          state.stores.read().unwrap().records.contains_key(c)
      });

  Resource id generation (in `runtime_api/wrappers.rs::generate_resource_id`)
  does *not* retry on collision today, so leave it alone — that's a
  separate question.

- **Behavior change?** no.

### F-008 — `#[allow(clippy::result_large_err)]` on functions that don't return `Result`

- **Category:** Dead code & API hygiene
- **Severity:** nice-to-have
- **Scope:** in-component (the symptom; the underlying lint sensitivity
  is also worth noting for the crate as a whole)
- **Location:** Roughly **31** sites in `admin_api/`. Examples:
  - `users.rs:78`, `users.rs:96`, `users.rs:118`, `users.rs:131`,
    `users.rs:193`, `users.rs:207`, `users.rs:251`, `users.rs:324` —
    all decorate functions whose return type is `Response<Full<Bytes>>`
    (not `Result`).
  - `pairs.rs:61`, `pairs.rs:90`, `pairs.rs:179` — same.
  - `policy.rs:174`, `policy.rs:194`, `policy.rs:264` — same.
  - `resources.rs:117`, `resources.rs:144`, `resources.rs:321`,
    `resources.rs:462` — same.
  - `stores.rs:230`, `stores.rs:292`, `stores.rs:309`, `stores.rs:499`,
    `stores.rs:513`, `stores.rs:599`, `stores.rs:1064`, `stores.rs:1167`
    — same.
  - `csrf.rs:127` (`resolve_principal`) and `auth.rs:239`
    (`handle_admin_password_change`) — these two **do** return
    `Result<_, Response<...>>` / take it via the body's flow, so they
    *might* be legitimate.

  `clippy::result_large_err` triggers on function signatures whose
  `Err` variant is larger than the configured threshold. A function
  that returns `Response<Full<Bytes>>` directly cannot be the lint's
  target. The allows on those functions look like leftovers from a
  point in time when the handlers returned `Result<_, _>`.
- **Recommendation:** Remove every `#[allow(clippy::result_large_err)]`
  whose target function does **not** have `-> Result<...>` in its
  signature. Re-run `cargo clippy --all-targets --workspace -- -D
  warnings` and add the allow back to the (small) set the lint still
  flags. If the lint genuinely fires on `admin_store()` or similar
  helpers, leave those — but the bulk of these are almost certainly
  dead.
- **Behavior change?** no.

### F-010 — Cascade ordering bug in `do_admin_client_instance_update` on remap

- **Category:** Complexity / correctness (behavioural)
- **Severity:** must-fix (in-epic — user folded into the refactor epic
  2026-05-22; gets its own task ticket so the behaviour change is one
  reviewable commit, not bundled with the F-003 naming sweep).
- **Scope:** in-component, behaviour change
- **Location:** `client_instances.rs:390-410`.
- **Observation:**

      instances.insert(id.to_string(), updated.clone());
      if let Err(e) = crate::runtime_clients::save_client_instances(
          &state.client_instances_file, &instances,
      ) {
          return error_response(StatusCode::INTERNAL_SERVER_ERROR, "write_client_instances_failed", ...);
      }
      drop(instances);
      if old_store_id != updated.current_store_id
          && let Err(e) = drop_client_instance_permissions(state, &old_store_id, id)
      {
          return error_response(
              StatusCode::INTERNAL_SERVER_ERROR,
              "internal",
              &format!("clearing prior-store permissions: {e:#}"),
          );
      }

  When the operator remaps a client instance to a different store, the
  in-memory map and the on-disk file are committed *first*; only after
  that does the policy-document cascade run. If the cascade fails the
  caller sees `500 internal` and (depending on retry behaviour) may
  assume the update didn't take. But the registry already holds the
  new mapping, and on next request `current_store_id` is the new
  store. The old store's policy document still carries the now-stale
  permissions for this client instance — which is *exactly* what
  `drop_client_instance_permissions` was added to prevent.

  Compare to the delete path (`handle_admin_client_instance_delete`,
  lines 471-482): there, the cascade is "best-effort + log and
  continue", with an explicit comment explaining the choice ("leaving
  orphaned policy rows is preferable to failing the delete and leaving
  the operator with no way to remove the client instance at all").

  Two cascades, two different failure handlings, in the same file.
  The update-path treatment is the wrong one: returning 500 doesn't
  actually undo the commit.
- **Recommendation:** Match the delete path's behaviour: log+continue
  on cascade failure, return `200 OK` with the update applied. Or, if
  the operator should know about the orphaned permissions, surface it
  in the response body (e.g. add a `partial_cascade_warning` field)
  rather than as an error status. **User decision 2026-05-22:** fold
  into the refactor epic as its own task ticket; apply the
  log-and-continue treatment to match the delete-path precedent
  (no wire-shape change).
- **Behavior change?** **yes** — kept as its own ticket inside the
  epic for diff clarity.
