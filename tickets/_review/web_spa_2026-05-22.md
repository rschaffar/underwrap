# Refinement review: web/ admin SPA

Date: 2026-05-22
Reviewer session: claude-opus-4-7[1m]
Scope: The `web/` Vite + React admin SPA in full — `web/src/api/` (typed
fetch client + ts-rs-generated types barrel), `web/src/components/`
(app-shell, policy-viewer-dialog, shadcn primitives in `ui/`),
`web/src/pages/` (9 page modules and their colocated `*.test.tsx`),
`web/src/router.tsx`, `web/src/App.tsx`, `web/src/main.tsx`,
`web/src/hooks/use-theme.ts`, `web/src/lib/` (`utils.ts`,
`error-message.ts`), `web/src/styles/globals.css`,
`web/src/test-setup.ts`, plus the build/test scaffolding
(`vite.config.ts`, `tsconfig.json`, `tailwind.config.ts`,
`playwright.config.ts`, `package.json`) and a structural read of
`web/e2e/`. The generated `web/src/api/types/*.ts` files are read for
shape only — they are regenerated by `cargo test --workspace` and
should not be edited by hand.

## Summary

- **33 findings** across 8 of the 10 review categories (no logging/observability
  findings; no security-boundary findings — the API client's no-log
  discipline is well-tested).
- **15 must-fix**, **18 nice-to-have**, **0 routed elsewhere**
  (F-016 — the `WrapperApprovalMode` cast cleanup — has been pulled
  into the ticket plan as 1570, with the matching Rust ts-rs
  annotation change as part of the same ticket; user has approved
  the backend touch).
- Proposed ticket shape: **epic + tasks**. There are 13 proposed
  tickets (12 in-scope + 1 repo-wide sweep), and four of them are
  page splits in the >700 LoC range — large enough that the epic
  structure carries its weight.

The SPA is in good shape overall: a clean shadcn/Tailwind/TanStack
foundation, a small typed fetch wrapper with no-log paranoia exercised
by unit tests, and broad RTL + Playwright coverage. The big drag on
the first-release look is page-module size: four `pages/*.tsx` files
are over 700 lines, three over 1000, because every page hosts all of
its dialogs inline. The duplicated patterns (store selector with URL
sync, three near-identical epoch formatters, the rose alert div, the
inline `<select>` styling, the unused `principal` prop) are all
straightforward extractions and account for most of the proposed
tickets.

### F-007 — Redundant import-then-reexport of 75 type names in `api/client.ts`

- **Category:** Dead code & API hygiene
- **Severity:** must-fix
- **Scope:** in-component
- **Location(s):** web/src/api/client.ts:125-265
- **Observation:** The file imports 75 type names from
  `@/api/types` (lines 125-194) and re-exports the same 75 names
  (lines 196-265). The body of the file only uses the imports
  internally; the re-exports exist so callers can write
  `from "@/api/client"` instead of `from "@/api/types"`. That's a
  ~140-line maintenance liability that has to be edited every time
  a Rust DTO is added or renamed (and the ts-rs generator already
  rewrites the barrel for them).
- **Recommendation:** Replace both blocks with
  `export type * from "@/api/types"` (TypeScript 5.0+, supported by
  the current 5.9.x), then keep the per-endpoint helpers
  importing internally from `@/api/types` directly. Existing
  callers that import types from `@/api/client` keep working.
- **Behavior change?** no — type-only re-export.
- **Related tickets:** F-006

### F-016 — `WrapperApprovalMode` cast soup (11 sites)

- **Category:** Complexity / type quality
- **Severity:** must-fix; **routed elsewhere — needs user sign-off**
  (the fix lives on the Rust side: the ts-rs annotation on
  `WrapperApprovalMode` in `crates/shared-protocol/src/policy.rs`)
- **Scope:** in-component (for the SPA cast removals) + backend (for
  the annotation change)
- **Location(s):**
  - Production: web/src/pages/wrapper-permissions.tsx:58, 590, 616,
    987, 990, 1001 (six casts, including `as unknown as` and
    `(mode as { until_epoch: bigint | number })`)
  - Tests: web/src/pages/wrapper-permissions.test.tsx:27, 35, 118-126,
    134-143 (five more)
- **Observation:** Every construction or destructuring of
  `WrapperApprovalMode` requires an `as` cast because the ts-rs
  output emits a structurally-untagged shape: the SPA needs a
  proper discriminated union
  `{ kind: "locked" } | { kind: "unlocked" } | { kind: "unlocked-until"; until_epoch: number }`
  so `kind`-switches narrow the type and the field accesses don't
  need `as`.
- **Recommendation:** On the Rust side, adjust the `#[ts(...)]`
  annotation on `WrapperApprovalMode` so ts-rs emits the
  discriminated union shape above (the wire shape itself stays
  the same — it's already a tagged union; only the TypeScript
  rendering changes). On the SPA side, drop every `as
  WrapperApprovalMode` and every `(mode as { until_epoch: ... })`
  field access.
- **Behavior change?** no on the wire; observable change is
  TypeScript-only. Routed to user for sign-off because it touches
  a generated DTO and the ts-rs golden file. A small backend
  ticket would land the annotation change; the SPA-side casts
  removal becomes a trivial follow-up.
- **Related tickets:** none

### `1570_task_clean_wrapper_approval_mode_typing.md`

**Title:** Clean up `WrapperApprovalMode` typing — drop SPA casts

**Resolves:** F-016, F-026

**Description:** The SPA constructs and destructures
`WrapperApprovalMode` in 11 places, every one of them carrying an
`as WrapperApprovalMode` or `as unknown as WrapperApprovalMode`
cast, plus a `(mode as { until_epoch: bigint | number }).until_epoch`
field-access cast at two sites. Two root causes:

1. TypeScript widens object literals: `{ kind: "locked" }` is
   inferred as `{ kind: string }`, not `{ kind: "locked" }`, so it
   doesn't fit the discriminated union without help. Fixable with
   `as const`, an explicit variable annotation, or a small
   discriminated-constructor helper.
2. `until_epoch: u64` is rendered by ts-rs as `bigint` in the
   generated TS, but the SPA passes `number` (`Math.floor(until /
   1000)`) and reads it back as a `number`. Forcing the field to
   `bigint` only on the type side (the wire is just a JSON number)
   creates the `as unknown as` casts.

Scope:

- **Rust:** add `#[ts(type = "number")]` to `until_epoch` in
  `crates/shared-protocol/src/policy.rs:47`:

  ```rust
  UnlockedUntil {
      #[ts(type = "number")]
      until_epoch: u64,
  },
  ```

  Run `cargo test --workspace` to regenerate
  `web/src/api/types/WrapperApprovalMode.ts` and update the
  `ts_export` golden if it surfaces.

- **SPA — drop every cast:**
  - `web/src/pages/wrapper-permissions.tsx:58` — `modeKind` no
    longer needs `as ModeKind`; the discriminated union narrows.
  - `web/src/pages/wrapper-permissions.tsx:590` — `<ModeBadge mode={{ kind: "locked" }} />` with no cast (the prop is
    typed `WrapperApprovalMode`, which accepts the narrowed
    literal).
  - `web/src/pages/wrapper-permissions.tsx:616, 938` — replace
    `(mode as { until_epoch: bigint | number }).until_epoch` with
    direct narrowing: `if (mode.kind === "unlocked-until") {
    const until = mode.until_epoch; … }`.
  - `web/src/pages/wrapper-permissions.tsx:982-1004` — the
    `switch (kind)` block: drop the `as` casts; the
    `unlocked-until` arm becomes `{ kind: "unlocked-until",
    until_epoch: Math.floor(until / 1000) }` (now a `number`).
  - Apply the same cleanups in
    `web/src/pages/wrapper-permissions.test.tsx:27, 35, 118-126,
    134-143` — the test fixtures construct mode literals the same
    way. The `1n` (bigint) at line 125 becomes `1`.

- **Decision needed** inside the task: if any other u64 timestamp
  field becomes load-bearing in this work, route the wider
  "render u64 timestamps as number" decision to a follow-up
  ticket. Stay narrow here: only `until_epoch`.
