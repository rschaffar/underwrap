### F-003 — Inconsistent verb style: stores/users/client-instances are REST, resources/pairs/secrets/wrapper-permissions are RPC

- **Category:** 2 — Naming & terminology / 7a — Simplification
- **Severity:** nice-to-have (decision needed)
- **Scope:** in-component
- **Location(s):**
  - REST style: `crates/backend-backendd/src/admin_api/users.rs:108-340`,
    `stores/crud.rs:41-340`, `client_instances.rs:124-440`
  - RPC style with `?store` in body: `resources.rs:41-291`,
    `pairs.rs:32-217`, `policy.rs:68-211`, `secrets.rs:48-285`
- **Observation:** Three subdomains expose
  `GET /v1/admin/<thing>` + `POST/PUT/DELETE /v1/admin/<thing>/{id}`.
  The other four expose `POST /v1/admin/<thing>/{action}` with the
  store name in the JSON body. The split exists because the second
  group is per-store-scoped, but every per-store call still has the
  same shape `{ store, ... }` — that's exactly what a path parameter
  is for. A unified `/v1/admin/stores/{store_id}/resources`,
  `…/pairs`, `…/secrets`, `…/wrapper-permissions` would:
  - move the store parameter where it can be cached by URL,
  - make the list endpoints `GET` again (cacheable, simpler client),
  - drop the `…ListRequest` wire types (one less DTO each),
  - put the store-locked / store-not-found `AdminError` mapping
    behind a single `admin_store(...)` extractor instead of every
    handler calling it by hand.

  The collapse also makes the OpenAPI spec read better — paths
  reflect the data model, instead of seven RPC tag groups whose
  identity is only visible in the path string.
- **Recommendation:** Decide whether to unify. If yes, the cutover
  is one ticket (greenfield, no compat). I would do it: it's a clear
  win for first-release polish and removes a category of
  inconsistency that future contributors will mirror.
- **Behavior change?** **yes — wire format change.** Path layout,
  HTTP methods, and request/response DTOs all move. Routed to the
  user for sign-off (CLAUDE.md flags wire-format changes as
  "permitted in greenfield, but never auto-ticketed").
- **Related tickets:** none.

### F-004 — `AdminError::admin` is a single-purpose constructor with a misleading name

- **Category:** 7a — Simplification
- **Severity:** nice-to-have
- **Scope:** in-component
- **Location(s):** `crates/backend-backendd/src/admin_api/error.rs:114-116`,
  used at `secrets.rs:65,93,118,136,164,168,236,239,241,278`,
  `policy.rs:85,119,179`
- **Observation:** `AdminError::admin` is a `400 admin_error` wrap
  that is used as `.map_err(AdminError::admin)` in two subdomains
  (secrets, policy) but nowhere else. The name reads like "the
  general admin error" but is actually "400 catch-all anyhow wrap"
  — easy to misread. It is also a borderline anti-pattern: each
  callsite is mapping an `anyhow::Error` that came back from a
  storage call (`load_resource_blob`, `load_policy_document`, etc.)
  and the same path in resources.rs/pairs.rs uses the explicitly
  named `AdminError::internal("loading X document", e)` (500)
  instead.

  So we have two storage-error mappings: secrets/policy → 400
  `admin_error`, resources/pairs → 500 `internal`. The 400 reading
  here is wrong; a backing-store read failure isn't a client error.
- **Recommendation:** Replace each `.map_err(AdminError::admin)` in
  `secrets.rs` and `policy.rs` with the same
  `AdminError::internal("loading X document", e)` pattern the other
  subdomains use, and remove the `AdminError::admin` constructor
  outright. The "legacy" justification cited in error.rs:109-114
  doesn't apply now that 1800 has shipped.

  (Discovery: when this constructor goes, `error.rs` shrinks by
  ~10 lines and the wire surface gets one fewer code string.)
- **Behavior change?** yes — these failure paths move from `400`
  to `500`. That is the right status for "store could not be read",
  but it is observable. Treat as a small correctness win and ship
  it in the same ticket.
- **Related tickets:** done/1800.

### F-005 — Repeated audit "map mutation result → log success/failure" scaffolding in user CRUD

- **Category:** 7 — Duplication / missed reuse
- **Severity:** nice-to-have
- **Scope:** in-component
- **Location(s):** `crates/backend-backendd/src/admin_api/users.rs:
  175-201, 232-256, 296-327, 348-376`
- **Observation:** Every user-CRUD handler ends in the same shape:

  ```rust
  match result {
      Ok(saved) => {
          log_admin_event("user.X", &principal,
              AuditEntity::User { username: ... }, None, "success");
          Ok(Json(...))
      }
      Err(e) => {
          let (reason, response) = classify_mutation_error(e);
          log_admin_event("user.X", &principal,
              AuditEntity::User { username: ... }, reason, "failure");
          Err(response)
      }
  }
  ```

  Four copies, identical except for the action string ("user.create",
  "user.update", "user.password.reset", "user.delete") and the
  username source. The same pattern appears with smaller variance
  in `client_instances.rs` (success-only path) and in `secrets.rs`
  (the inline `let result = if outcome.is_ok() { "success" } else
  { "failure" };` blocks).
- **Recommendation:** Extract a `audit_user_mutation_result(action,
  &principal, &username_source, result) -> Result<T, AdminError>`
  helper that owns the success/failure split and the
  `classify_mutation_error` call. Each handler ends in
  `audit_user_mutation_result("user.create", &principal,
  &target_username, result).map(|saved| Json(user_list_item(&saved)))`.

  Net: ~80 lines of repeated scaffolding collapse to ~20. A reader
  sees the action string once per handler rather than three times.
- **Behavior change?** no.
- **Related tickets:** done/1820 (audit consolidation).

### F-013 — Wrapper-permissions page does 5 round-trips per visit; could be 3

- **Category:** 7a — Simplification (server side) / CRUD shape mismatch
- **Severity:** nice-to-have (decision needed)
- **Scope:** in-component
- **Location(s):**
  - `web/src/pages/wrapper-permissions/page.tsx:41-62` —
    `stores`, `permissions`, `pairs`
  - `web/src/hooks/use-store-lookups.ts:25-33` — `resources`,
    `client_instances`
- **Observation:** Visiting `/wrappers` for store X fires:
  1. `GET /v1/admin/stores`
  2. `POST /v1/admin/wrapper-permissions/list { store }`
  3. `POST /v1/admin/pairs/list { store }`
  4. `POST /v1/admin/resources/list { store }`
  5. `GET /v1/admin/client-instances`

  Three of those (#2, #3, #4) load the per-store
  policy/pairs/resources documents — every one is a separate
  storage read on the backend side. The data dependencies are
  fixed: rendering the table needs all three sets at once. A single
  `GET /v1/admin/stores/{id}/wrapper-permissions-view` returning
  `{ pairs, permissions, resources }` halves the round-trip count
  on a busy page.

  The `secrets` page has a similar shape: secrets/list + resources/
  list + client-instances are loaded on mount.
- **Recommendation:** Decide whether to add aggregate read
  endpoints. If F-003 is approved, this collapses naturally
  (`GET /v1/admin/stores/{id}/wrapper-permissions-view`); if not,
  it's still a sensible standalone server-side join. I would not
  push for this independently — three reads in a single TLS
  session over localhost is cheap — but it is a textbook
  "CRUD shape mismatch" and worth flagging.
- **Behavior change?** yes — adds new endpoint. Routed to user.
- **Related tickets:** none.

### 1950_task_unify_admin_api_to_rest_shape.md

**Title:** Unify admin API on REST shape: collapse RPC `…/list`,
`…/create`, `…/delete`, `…/rename` endpoints onto
`GET /v1/admin/stores/{id}/<thing>` family

**Description:** Today three subdomains expose REST
(`/v1/admin/users`, `/v1/admin/stores`, `/v1/admin/client-instances`)
while four expose RPC with the store in the JSON body
(`/v1/admin/resources/{list,create,delete,rename}`,
`/v1/admin/pairs/{list,create,delete}`,
`/v1/admin/secret/{list,read,write,delete,rename}`,
`/v1/admin/wrapper-permissions/{list,upsert,delete}`).

Cut over to a single shape:

- `GET    /v1/admin/stores/{id}/resources`               (list)
- `POST   /v1/admin/stores/{id}/resources`               (create)
- `PUT    /v1/admin/stores/{id}/resources/{rid}`         (rename)
- `DELETE /v1/admin/stores/{id}/resources/{rid}`         (delete)
- `GET    /v1/admin/stores/{id}/pairs`                   (list)
- `POST   /v1/admin/stores/{id}/pairs`                   (create)
- `DELETE /v1/admin/stores/{id}/pairs/{wrapper}/{rid}`   (delete)
- `GET    /v1/admin/stores/{id}/wrapper-permissions`     (list)
- `PUT    /v1/admin/stores/{id}/wrapper-permissions/{client_instance}/{wrapper}/{rid}` (upsert)
- `DELETE /v1/admin/stores/{id}/wrapper-permissions/{client_instance}/{wrapper}/{rid}` (delete)
- `GET    /v1/admin/stores/{id}/secrets`                 (list)
- `GET    /v1/admin/stores/{id}/secrets/{rid}/{slot}/{key}` (read)
- `PUT    /v1/admin/stores/{id}/secrets/{rid}/{slot}/{key}` (write)
- `POST   /v1/admin/stores/{id}/secrets/{rid}/{slot}/{key}/rename` (rename — keeps a body for `to_key`)
- `DELETE /v1/admin/stores/{id}/secrets/{rid}/{slot}/{key}` (delete)

Drop the now-redundant DTOs (`Admin*ListRequest`,
`Admin*DeleteRequest`, etc.) — the path parameters carry the
identity. Move the store-locked / store-not-found mapping behind a
single `AdminStorePath` extractor that wraps `admin_store(...)` so
each handler stops repeating it.

Greenfield posture explicitly permits this. Includes:
- Rust route refactor across all four RPC subdomains
- DTO pruning in `shared-protocol::service`
- OpenAPI regeneration (`openapi.json` checked in)
- SPA `web/src/api/client.ts` helpers rewired
- Every page/dialog callsite updated

Also folds in **F-009** (path-param rename `name` → `id` on the
`stores/{name}` family) since the URLs are being cut over anyway —
all stores routes land in their final shape in one pass.

**Resolves:** F-003, F-009

**Acceptance:** `cargo test --workspace`, `cargo clippy
--all-targets --workspace -- -D warnings`, OpenAPI drift test
green, `cd web && npm test`, `cd web && npm run test:e2e` (inside
`nix develop`), `nix build .#checks.x86_64-linux.vm-test`.
